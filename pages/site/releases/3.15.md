## Release highlights

### Java 25

Gerrit is now built and tested with JDK 25 by default, producing Java 25
bytecode (major version 69).
<!-- REVIEW: confirm resulting Java 25 runtime requirement (inferred from bytecode version 69) -->

The optional `java21` Bazel configuration is still available to build and
release Gerrit for Java 21 (`bazel build --config=java21 release`).

### Rich Markdown Diff

A rich rendered view for the diff of Markdown files has been introduced, which
can be toggled from the diff view and the file list, with inline word and block
highlighting.

Comments can be added directly in the rendered Markdown view, including with
the `C` shortcut and on a text selection.

### Stack Diff

An experimental Stack Diff dialog, opened from the Relation Chain section, shows
the cumulative file list and diff of a whole relation chain against its base
parent commit, so the combined changes of a stack can be reviewed in one place.
Enable it with the `UiFeature__stack_diff` experiment.

### Submit Requirement Templates

Administrators can now define reusable submit requirement templates in
`[submit-requirement-template "<name>"]` sections of `project.config`, which
project owners can pick from in the UI when creating submit requirements.

Templates are inherited from parent projects and exposed through the new
`GET /projects/{project}/submit_requirements_templates` and
`GET /projects/{project}/submit_requirements_templates/{name}` REST endpoints.

### Searching Changes

New search operators have been added to the change index:

* `onlypaths:` finds changes touching exactly the given set of files,
  allowing submit requirements to replace Prolog rules based on the
  exact list of modified files. Magic files such as `/COMMIT_MSG` are ignored, and
  a single regular expression starting with `^` can be used instead of a
  comma-separated list of paths.

  > **NOTE**: Using the operator with a very commonly changed file may produce a
  > large intermediate result set and be expensive.

* `filecount:` finds changes whose latest patch set touches a given number of
  files, e.g. `filecount:>2`.

* `unmet_requirement:'NAME'` and `unsatisfied_requirement_count:'RELATION''NUMBER'`
  find changes by their unmet submit requirements. These operators are not
  allowed inside submit requirement expressions.

* `has:hashtag` matches changes that carry at least one hashtag.

### Committing Files to a Branch via REST API

The new `POST /projects/{project-name}/branches/{branch-id}/commit` REST
endpoint creates, updates, deletes or renames files on a branch in a single
commit, without cloning the repository or creating a change.

The caller needs Push access on the branch; commit and ref-update validators
(including plugin validators) run, but push-only receive-pack checks are not
applied and matching open changes are not auto-closed.

An optional `base_revision` rejects the request with `409 Conflict` if the
branch has moved, and a request that would not change the tree is rejected with
`400 Bad Request`.

### OAuth Tokens Lifecycle

The handling of OAuth tokens has been extended across the whole token lifecycle:

* **PKCE**:
  the `OAuthServiceProvider` extension point now supports OAuth 2.0 with PKCE
  (Proof Key for Code Exchange). Providers can return an `OAuthAuthorizationInfo`
  with both the authorization URL and the generated code verifier, and receive
  the verifier back through an overloaded `getAccessToken()` method. Existing
  providers remain compatible through default interface methods.

* **Token refresh**:
  Gerrit can now renew expired OAuth access tokens from their refresh token when
  the provider supports it, through the new `OAuthServiceProvider.supportsRefresh()`
  and `refresh()` methods. After a failed refresh, Gerrit waits for
  `auth.oauthTokenRefreshInterval` (default 5 minutes) before retrying for that
  account. `GET /accounts/{account-id}/oauthtoken` also renews an expired token
  and returns `404 Not Found` if it cannot be renewed, without evicting the
  cached entry.

* **Encryption at rest**:
  OAuth tokens stored in the `oauth_tokens` cache are now encrypted with
  AES-256-GCM by default through a built-in `OAuthTokenEncrypter`. The key is
  configured with `auth.tokenEncryptionKey` in `secure.config`; for sites using
  `auth.type = OAUTH`, `init` (including the upgrade `init` run) generates it
  automatically when not set. If the key is unset, tokens are stored in cleartext
  and a warning is logged at startup; entries written in cleartext before the key
  was set remain readable.

* **Token revocation**:
  new `OAuthServiceProvider.supportsRevoke()` and `revoke(OAuthToken)` default
  methods and a new `OAuthTokenRevokedListener` extension point, notified when an
  account's or all tokens are revoked. An `OAuthTokenRevoker` revokes a token at
  the issuing provider and evicts it from the `oauth_tokens` cache.
  <!-- REVIEW: OAuthTokenRevoker not referenced by any endpoint/command at HEAD -->

### Administration & Configuration

* **Stale change index recovery**

  Gerrit can now automatically recover change index updates that were lost when
  the process crashed or was interrupted between the NoteDb write and the index
  write. Enable it with `index.staleChangeRecovery = true` (default `false`):
  Gerrit writes per-change intent files under `$site_path/data/pending-index/`,
  recovers leftovers from a crashed process at startup and runs a background
  scanner every `index.staleChangeRecoveryInterval` (default `5m`).

  > **NOTE**: Recovery is only effective when `index.commitWithin` is set to zero
  > and `index.indexChangesAsync` is false.

* **Index directory**

  The new `index.directory` setting configures where Gerrit stores its index
  independently of the site path (default `$site_path/index`; relative paths are
  resolved against `$site_path`).

## Important Notes

### Schema and index changes

Gerrit schema version has been upgraded from `185` to `186`: the migration
grants the new `postReviewComment` permission on `refs/*` to Registered Users
in `All-Projects`.

The Changes index has been upgraded from `v88` to `v90` and requires a full
reindex:

* `v89` adds the indexed fields for the new `unmet_requirement` and
  `unsatisfied_requirement_count` search operators.
* `v90` adds the file count field for the new `filecount:` search operator.

### Online upgrade with zero-downtime

//TODO - NEEDS TESTING

<!-- REVIEW: NoteDb schema changed, confirm zero-downtime upgrade is still supported -->

Gerrit v3.15.x supports zero-downtime upgrade from Gerrit v3.14 when configured
using a
[high-availability](https://gerrit.googlesource.com/plugins/high-availability/+/refs/heads/master/README.md)
setup.

During the zero-downtime upgrade, Gerrit end-users will not experience any
outage or service disruption and will be able to perform any read/write Gerrit
operation seamlessly.

The zero-downtime upgrade process for high-availability setups
consists of the following steps ([demo](https://youtu.be/vK5qsb0W7q4)):

1. Have Gerrit servers running v3.14 in high-availability
   configuration, healthy and able to handle the incoming traffic properly.
2. Set one of the Gerrit servers to unhealthy.
3. Shutdown the Gerrit server, update gerrit.war, plugins and libs to v3.15.x and start Gerrit again.
4. Verify that the Gerrit server is working properly (e.g. run automated smoke
   tests) and then make it healthy again.
5. Ensure the Gerrit server is fully caught up with the events that happened while
   it was down before directing traffic to it.
6. Repeat steps 2 to 6 for each of the remaining Gerrit servers.

### Known issues

* [Issue 454695136](https://issues.gerritcodereview.com/issues/454695136)
  Upgrade to new H2 v2 storage backend for persistent caches can cause corrupt
  cache files upon forced JVM shutdown.

  The new H2 library brings multi-threaded operations, but also [one critical
  issue](https://github.com/h2database/h2database/issues/4083), reported on cache

  > does not exit within the shutdown timeout.

  Whilst the problem is investigated, you may consider using alternative persistent cache backends like:
  - [cache-chroniclemap](https://gerrit.googlesource.com/modules/cache-chroniclemap/)
  - [cache-postgres](https://gerrit.googlesource.com/modules/cache-postgres) -

  > **NOTE: This is not actively maintained, consider further testing before rolling out**

  <!-- REVIEW: still open? -->

* [Issue 309098227](https://issues.gerritcodereview.com/issues/309098227) [Change 360646](https://gerrit-review.googlesource.com/360646):
The introduction of a per-request ref cache for better performance may break
the repository consistency

  The addition of a new `core.usePerRequestRefCache` setting, true by
  default, introduced a per request (currently per request thread) ref
  cache, helping reduce the overhead of checking if the packed-refs file
  was outdated. However, in some scenarios, such as multi-site or
  concurrency between `git-receive-pack` and `git-gc`, it may lead to
  split-brain inconsistencies and, in the worst-case scenario, to the
  corruption of the underlying repository.

* [Issue 380898784](https://issues.gerritcodereview.com/issues/380898784):
The new `changes_by_project` cache will make the `git-upload-pack` fail intermittently
on projects containing one or more inconsistent changes.

  The introduction of the `changes_by_project` cache is incompatible with projects
  having one or more inconsistent changes, like changes with /meta refs coming from
  unexpected Gerrit serverId.
  The cache makes the `git-upload-pack` fail intermittently
  with internal server errors when it fails to load the change meta-data depending
  on the status of the cache.
  As a workaround, disable the `changes_by_project` cache as follows in `gerrit.config`:
  ```
  [cache "changes_by_project"]
        memoryLimit = 0
  ```

## Breaking Changes

* [Change 580605](https://gerrit-review.googlesource.com/c/gerrit/+/580605):
  The obsolete `contrib/git-exproll.sh` repository maintenance script has been
  removed.
  <!-- REVIEW: contrib script removal; could be Other/minor rather than Breaking -->

  Administrators still relying on it should use the geometric repacking features
  of `git repack` instead, which provide a similar and mostly better approach.

* [Issue 507078595](https://issues.gerritcodereview.com/issues/507078595),
  [Issue 515272357](https://issues.gerritcodereview.com/issues/515272357):
  The `config/server/index.changes` REST API (`delete_missing` option) now only
  accepts change identifiers in `project~changeNumber` format when
  `delete_missing` is `true`, preventing ambiguous identifiers from deleting the
  wrong change from the index, and correctly deletes changes missing from
  NoteDb identified in that format.

  If any of the change identifiers is in a different format, the request fails
  with `400 Bad Request` and none of the operations are executed.

* [Change 607261](https://gerrit-review.googlesource.com/c/gerrit/+/607261):
  Disk stats for persistent caches are no longer collected by default by the
  `show-caches` SSH command and the List Caches REST API.

  Collecting disk stats is expensive on busy servers with large caches; use the
  new `--include-diskstats` option of `show-caches`, or `include-diskstats=true`
  on `GET /config/server/caches/`, to include them.

* [Change 614843](https://gerrit-review.googlesource.com/c/gerrit/+/614843):
  Work-in-progress changes created via the REST API (`POST /changes/`) now
  default to notifying only the owner, so project watchers are no longer emailed
  about them unless `notify` is explicitly set.
  <!-- REVIEW: default notification behaviour change; could alternatively be listed under Bug fixes -->

  The `notify` field of `ChangeInput` no longer defaults to `ALL`; when
  unspecified it defaults to `OWNER` for WIP changes and `ALL` for ready
  changes, matching the behaviour of pushes with `%wip`.

* [Change 617061](https://gerrit-review.googlesource.com/c/gerrit/+/617061):
  Replies in a comment thread must now be on the same patchset as the parent
  comment, enforced by the backend for REST API requests.

  Requests that set `in_reply_to` to a comment on a different patchset are now
  rejected with `400 Bad Request`; clients replying to comments on several
  patchsets in one `POST review` call must split the request by patchset.

* [Issue 40009784](https://issues.gerritcodereview.com/issues/40009784):
  Implicit merges are now rejected on submit by default, not only on push.
  <!-- REVIEW: confirm upgrade guidance wording about setting the option to false -->

  The `receive.rejectImplicitMerges` project option now applies to both push and
  submit, and its effective default is `true` when no project overrides it.

  The former `GerritBackendFeature__*_implicit_merges_on_merge` experiments have
  been removed; projects that intentionally rely on implicit merges must set
  `receive.rejectImplicitMerges = false`.

* [Change 622261](https://gerrit-review.googlesource.com/c/gerrit/+/622261):
  Fix `httpd.acceptorThreads` being applied to Jetty selector threads, and add
  the new `httpd.selectorThreads` option to control the selector thread count.

  `httpd.acceptorThreads` now defaults to 0 (selector threads also accept new
  connections) and `httpd.selectorThreads` defaults to 2, preserving the
  previous effective behavior.

  Sites that raised `httpd.acceptorThreads` to increase I/O concurrency should
  set `httpd.selectorThreads` instead to keep the same selector count.

* [Change 581562](https://gerrit-review.googlesource.com/c/gerrit/+/581562):
  The `gerrit_plugin` Bazel rule no longer accepts the `provided_deps`
  attribute, keeping it in sync with bazlets which dropped support for it.
  <!-- REVIEW: plugin build API removal; may fit Plugin changes instead of Breaking -->

  Plugins built in-tree that still pass `provided_deps` to `gerrit_plugin` need
  to remove that attribute from their BUILD files.

* [Change 553022](https://gerrit-review.googlesource.com/c/gerrit/+/553022),
  [Change 553181](https://gerrit-review.googlesource.com/c/gerrit/+/553181):
  The web UI no longer sets up the global `Polymer` variable and Polymer bridges
  that plugins previously relied on.
  <!-- REVIEW: plugin impact inferred from removed gr-app.ts comment "Sets up global Polymer variable, because plugins requires it" -->

  Gerrit UI plugins that still depend on the globally available Polymer library
  will no longer work and must be migrated to Lit.

  The `@polymer/polymer` and `polymer-bridges` dependencies have been removed
  from the web UI and from the plugins build, keeping only
  `@polymer/font-roboto-local`.

* [Change 626021](https://gerrit-review.googlesource.com/c/gerrit/+/626021):
  In the Java extension API, `RevisionInfo.ParentInfo#changeStatus` is now typed
  as the `ChangeStatus` enum instead of `String`.

  The JSON returned by the REST API is unchanged, but Java extension and plugin
  code reading this field must be adapted.

* [Change 630241](https://gerrit-review.googlesource.com/c/gerrit/+/630241):
  Add `OAuthTokenCache.getEvenIfExpired()` so refresh-aware callers can read an
  expired token's refresh token, and rename `OAuthTokenCache.get()` to
  `getOrEvictIfExpired()` with unchanged behavior.
  <!-- REVIEW: rename of get() may break plugins calling OAuthTokenCache.get() -->

* [Change 631582](https://gerrit-review.googlesource.com/c/gerrit/+/631582),
  [Change 632561](https://gerrit-review.googlesource.com/c/gerrit/+/632561):
  `LockManager` locks are now identified by namespaced `LockKey`s to prevent
  unrelated callers from colliding on the same lock name, and all core callers
  obtain `LockManager` through its `DynamicItem`, so plugin overrides of the
  `LockManager` extension point are honored consistently.

  `LockManager.getLock(String)` is deprecated in favour of `getLock(LockKey)`;
  plugins should create keys with `LockKey.plugin(...)`.

* [Change 631801](https://gerrit-review.googlesource.com/c/gerrit/+/631801):
  `DynamicSet.contains()` is deprecated, with a warning that its execution is
  inherently slow.

## Performance Changes

* [Change 573862](https://gerrit-review.googlesource.com/c/gerrit/+/573862),
  [Change 573902](https://gerrit-review.googlesource.com/c/gerrit/+/573902),
  [Change 573961](https://gerrit-review.googlesource.com/c/gerrit/+/573961),
  [Change 573981](https://gerrit-review.googlesource.com/c/gerrit/+/573981),
  [Change 633783](https://gerrit-review.googlesource.com/c/gerrit/+/633783):
  The web UI no longer requests expensive diff statistics when loading all
  revisions for the patchset picker, polling for change updates, listing
  cherry-picks and in several change-list queries, using the `SKIP_DIFFSTAT`
  option, which the server now also honors for revision file lists with
  `ALL_REVISIONS` and `ALL_FILES`.

* [Change 573861](https://gerrit-review.googlesource.com/c/gerrit/+/573861):
  High-priority UI requests, such as sending a review, now bypass the frontend
  write-request scheduler queue to reduce UI latency under congestion.

* [Change 573881](https://gerrit-review.googlesource.com/c/gerrit/+/573881),
  [Change 590121](https://gerrit-review.googlesource.com/c/gerrit/+/590121):
  Format ChangeInfo results and load change data in parallel in a thread-safe
  way, significantly speeding up REST queries returning many changes.

* [Change 585386](https://gerrit-review.googlesource.com/c/gerrit/+/585386):
  Persistent disk caches can be opened in parallel during startup, shortening
  the time in which cache misses require a full H2 lookup because the
  BloomFilter is not yet built.

  Set `cache.startupThreads` to a value greater than 1 to open caches in a
  dedicated `DiskCache-Startup` thread pool; the default of 1 keeps sequential
  opening. On a production instance, 5 threads reduced cache startup time from
  ~70 minutes to ~22 minutes.

* [Change 593661](https://gerrit-review.googlesource.com/c/gerrit/+/593661):
  The AI prompt dialog now loads and processes the change's patch content only
  when it is opened, avoiding a browser freeze on page load for very large
  changes when AI review is enabled.

* [Change 598361](https://gerrit-review.googlesource.com/c/gerrit/+/598361):
  Creating and updating draft comments reuses the already loaded change notes
  instead of reopening the repository and resolving the change meta ref again.

* [Change 600221](https://gerrit-review.googlesource.com/c/gerrit/+/600221):
  Speed up expanded-file lookups in the change file list by tracking expanded
  files as a set of paths, which helps changes with many files.

* [Change 609041](https://gerrit-review.googlesource.com/c/gerrit/+/609041):
  SSH change queries now stop processing results promptly when the client
  disconnects, instead of continuing to build output that will never be sent.

* [Change 591501](https://gerrit-review.googlesource.com/c/gerrit/+/591501):
  Speed up building H2 persistent cache bloom filters at startup by reading the
  H2 file up front to warm the OS page cache.

  On a production instance with ~84M disk cache entries this reduced loading
  time from ~22 to ~16 minutes.

* [Change 607281](https://gerrit-review.googlesource.com/c/gerrit/+/607281):
  Warm the OS page cache before collecting disk stats of H2 persistent caches,
  reducing cold-read latency for large caches.

* [Change 601281](https://gerrit-review.googlesource.com/c/gerrit/+/601281):
  Patch set events now compute insertions and deletions from the `diff_summary`
  cache instead of loading full file diffs.
  <!-- REVIEW: event size values change; consider Breaking Changes -->

  As a result, the `COMMIT_MSG` and `PATCHSET_LEVEL` files are no longer counted
  in the reported size, restoring the originally intended behavior.

* [Change 619761](https://gerrit-review.googlesource.com/c/gerrit/+/619761):
  Avoid re-evaluating submit rules on open changes when both strict and lenient
  submit records are requested, reusing the records cached on the change data.

* [Change 619706](https://gerrit-review.googlesource.com/c/gerrit/+/619706):
  Reduce NoteDb access when loading change data by keeping patch sets loaded
  from the index, caching the resolved meta revision and no longer loading all
  patch sets to compute `reviewedBy`.

* [Change 619705](https://gerrit-review.googlesource.com/c/gerrit/+/619705):
  Speed up the "Submitted Together" computation by returning immediately for
  standalone changes, without evaluating submit rules, and by removing the
  sequential pre-computation of submit records for multi-change sets.

* [Change 619704](https://gerrit-review.googlesource.com/c/gerrit/+/619704):
  Speed up NoteDb change notes parsing by matching commit footers without
  allocations and streamlining the parser, with a measured ~9-10% latency
  reduction and lower heap churn.

* [Change 621764](https://gerrit-review.googlesource.com/c/gerrit/+/621764):
  Avoid duplicate concurrent REST requests for the same account details when
  several UI components request them at the same time.
  <!-- REVIEW: commit says Release-Notes: skip -->

* [Change 619707](https://gerrit-review.googlesource.com/c/gerrit/+/619707):
  Comment listing and formatting is faster thanks to fewer redundant
  comment-context key computations and allocations, with benchmarks on 5,000
  comments showing up to 1.9x faster formatting.

* [Change 623341](https://gerrit-review.googlesource.com/c/gerrit/+/623341):
  Change queries no longer issue a redundant secondary index query when all

* [Change 619762](https://gerrit-review.googlesource.com/c/gerrit/+/619762):
  Group lookups are faster thanks to batched group index queries by UUIDs and

* [Change 626801](https://gerrit-review.googlesource.com/c/gerrit/+/626801):
  Git pushes by non-service users now benefit from asynchronous change indexing
  when `index.indexChangesAsync` is enabled, as the push access path is now
  preserved when materializing the user.

  The `index.indexChangesAsync` documentation is updated accordingly.

* [Change 630261](https://gerrit-review.googlesource.com/c/gerrit/+/630261):
  Commit validation on push no longer performs rename detection when counting
  changed files, making `change.maxFiles` validation about 4x faster for commits
  with many files.

  Without rename detection, a renamed file now counts as two changed files (one
  deletion and one addition) against `change.maxFiles`.

* [Change 633782](https://gerrit-review.googlesource.com/c/gerrit/+/633782):
  Avoid reopening the Git repository and recreating readers twice per revision
  when listing modified files against a parent, by reusing the already open
  RevWalk.

* [Change 633784](https://gerrit-review.googlesource.com/c/gerrit/+/633784):
  Keep a user's computed group membership cached across all labels when
  computing permitted labels for change details, instead of recomputing it for
  every label and reviewer.

* [Change 633785](https://gerrit-review.googlesource.com/c/gerrit/+/633785):
  Remove a quadratic scan over patch sets when computing the change kind for
  `ALL_REVISIONS` requests, and open the repository once and share it across all
  revisions.

* [Change 633786](https://gerrit-review.googlesource.com/c/gerrit/+/633786):
  Defer the submission index query used to compute the revert-submission action
  until project state and the `CREATE_CHANGE`/`REVERT` permissions have been
  checked, and fetch only matching change IDs.

* [Change 638024](https://gerrit-review.googlesource.com/c/gerrit/+/638024):
  On JDK 25, Gerrit site init now enables compact object headers (JEP 519) by
  default to reduce heap usage.
  <!-- REVIEW: changes init-written default JVM options; consider New Features or Breaking Changes -->

  Init adds `-XX:+UseCompactObjectHeaders` to `container.javaOptions` in
  `gerrit.config`, also on existing sites, unless the option is already
  explicitly enabled or disabled.

  To opt out persistently, set `-XX:-UseCompactObjectHeaders`, as simply
  removing the option causes the next init on JDK 25 to add it back.

## Permissions & Security Changes

* [Change 599041](https://gerrit-review.googlesource.com/c/gerrit/+/599041):
  The account query REST endpoint now enforces account visibility, no longer
  returning accounts that the caller cannot see when `o=DETAILS` is used or for
  suggest queries.

* [Change 609682](https://gerrit-review.googlesource.com/c/gerrit/+/609682):
  The account query REST API now enforces `accounts.visibility` and, when
  visibility is restricted (`SAME_GROUP`, `VISIBLE_GROUP` or `NONE`), no longer
  exposes detailed account information (`o=DETAILS` and suggest) to
  unauthenticated callers.

* <!-- REVIEW: no change found for b91e7ecf5651b5bb2c8322c8393d80901b20d306 -->:
  Submit requirement predicates evaluated asynchronously on worker threads now
  run as the user selected by the caller, preserving the caller's security
  context.

* [Issue 561066231](https://issues.gerritcodereview.com/issues/561066231):
  Setting `cache.oauth_tokens.memoryLimit = 0` now fully disables OAuth token
  storage, so tokens are no longer written to the persistent H2 cache even when
  `diskLimit` is positive.

  When token storage is disabled, `GET /accounts/{id}/oauthtoken` returns `409
  Conflict`. To keep tokens in memory only, set `cache.oauth_tokens.diskLimit =
  0`; if tokens were previously written to disk, stop Gerrit and remove the
  existing `oauth_tokens` persistent cache files.

  The storage contract for `OAuthTokenEncrypter` implementations is now
  documented: `token`, `secret` and `raw` are secret fields, while `expiresAt`
  and `providerId` stay in cleartext.

* [Change 633202](https://gerrit-review.googlesource.com/c/gerrit/+/633202):
  Change notification emails now show the sender's email address alongside the
  display name in action sentences, so a generic or deceptive display name can
  no longer make actions appear to come from someone else.
  <!-- REVIEW: may affect custom email templates relying on fromName -->

  The `fromName` variable of change email templates now has the form `Name
  <email>`.

* [Issue 565075161](https://issues.gerritcodereview.com/issues/565075161):
  Replace all uses of the legacy `SHA1PRNG` random generator with the platform
  default `SecureRandom` for OAuth state, signed-push seed, auth-token and
  Change-Id generation, and salt generated group UUIDs and patch-set approval
  UUIDs with cryptographically strong random bytes instead of `Math.random()`.

## New Features

* [Change 609281](https://gerrit-review.googlesource.com/c/gerrit/+/609281):
  The H2-based `accountPatchReviewDb` can now be shared safely by multiple
  Gerrit primaries on a shared filesystem (e.g. NFS) without an external
  database. Set `accountPatchReviewDb.h2LockType = jgit` to replace H2's built-in
  file locking with JGit-style `.lock` files; `accountPatchReviewDb.h2LockTimeout`
  (default `30 seconds`) controls how long to retry acquiring the lock.

* [Change 541701](https://gerrit-review.googlesource.com/c/gerrit/+/541701):
  Add project-level REST endpoints to diff two commits without a change context:
  `GET /projects/{project}/commits/{commit-id}/diff?name-only&base={sha1}` lists
  the files that differ and `GET
  /projects/{project}/commits/{commit-id}/files/{file}/diff?base={sha1}` returns
  the diff of a single file.

  This allows comparing commits across a relation chain, e.g. to see the
  cumulative changes from the base of a chain to any change in it; responses use
  the same `FileInfo`/`DiffInfo` format as the change-level diff. The
  `name-only` parameter is currently required. The commits must be in an
  ancestor/descendant relationship and all commits in the path must be visible
  to the caller.

* [Change 561921](https://gerrit-review.googlesource.com/c/gerrit/+/561921),
  [Change 562981](https://gerrit-review.googlesource.com/c/gerrit/+/562981):
  Add a configurable timeout for submit requirement evaluation so that slow or
  expensive expressions cannot block access to a change.

  The new `submitRequirement.executionTimeout` option (default 0, no timeout)
  applies per submit requirement to the combined evaluation of `applicableIf`,
  `submittableIf` and `overrideIf`; when exceeded the evaluation is aborted, the
  expression result gets the new `TIMEOUT` status and the change cannot be
  submitted. Evaluation runs on a dedicated executor sized by the new
  `submitRequirement.evaluationThreads` option (default -1, evaluation in the
  request thread, in which case the timeout does not apply; 0 uses the number of
  available CPUs).

  Submit requirements whose evaluation exceeds
  `submitRequirement.executionTimeout` now report the new `TIMEOUT` status in
  the change REST API instead of `UNSATISFIED`, and the UI recognizes it.

  REST API clients that inspect `submit_requirements.status` should handle the
  new `TIMEOUT` value.
