## Release highlights

### Enhanced AI Review metadata Integration & Review Agent Support

Introduced a major revamp to the first-class support for AI-driven code
review workflows. Human comments and AI-generated feedback can now be
clearly distinguished thanks to the new native `isAi` boolean field in
NoteDb.

The Gerrit UI leverages this by rendering a distinctive "sparkle" icon
next to AI-generated comments and check results. To streamline feedback
loops on automated reviews, change owners are now presented with a quick
"Disagree" action button on standalone AI comments.

To support the growing ecosystem of AI plugins, the UI introduces a new
dedicated plugin endpoint (`chat-panel`) in the AI chat view sidebar,
alongside a new `change-view-commit-aside` endpoint for displaying
high-level AI rationales.

Security around these automated agents has also been tightened: the
`aiReview` permission has been transitioned to a standard default-deny
ACL model, ensuring tighter administrative control over which projects and
branches are exposed to AI review agents.

A new feature flag (`GerritBackendFeature__allow_ai_review_for_registered_users`)
allows the preservation of the previous, more permissive permission system
for AI interaction that allows any registered user to access the AI button
and chat regardless of the explicit `AI Review` permission.

### Java 25

Gerrit is now built and tested with JDK 25 by default, producing Java 25
bytecode (major version 69).

The optional `java21` Bazel configuration is still available to build and
release Gerrit for Java 21 (`bazel build --config=java21 release`).

### Bazel modules

The migration of Gerrit's build to [Bazel modules](https://bazel.build/external/migration)
(Bzlmod), started in Gerrit 3.14, is now complete: the legacy `WORKSPACE`-based
dependency mechanism, including `external_plugin_deps.bzl` and the `maven_jar`
rule, has been removed, the web UI build has also moved to Bazel modules, and
Gerrit is built with Bazel 9, where Bazel modules are the only supported
dependency model.

**All plugins must move to Bazel modules.** Plugins that still declare their
external dependencies in `external_plugin_deps.bzl` no longer build and must
declare them in their own `MODULE.bazel` with `rules_jvm_external`, as described
in [Plugins with external dependencies](https://gerrit-documentation.storage.googleapis.com/Documentation/3.15.0/dev-build-plugins.html#_plugins_with_external_dependencies).

### Stack Diff

An experimental _Stack Diff_ dialog, opened from the Relation Chain section, shows
the cumulative file list and diff of a whole relation chain against its base
parent commit, so the combined changes of a stack can be viewed in one place, similar
to PRs.
Enable it with the `UiFeature__stack_diff` experiment.

### Submit Requirement Templates

Administrators can now define reusable submit requirement templates in
[`[submit-requirement-template "<name>"]`](https://gerrit-documentation.storage.googleapis.com/Documentation/3.15.0/config-submit-requirements.html#submit-requirement-template-subsection)
sections of `project.config`, which project owners can pick from in the UI when
creating submit requirements.

Templates are inherited from parent projects and exposed through the new
[`GET /projects/{project}/submit_requirements_templates`](https://gerrit-documentation.storage.googleapis.com/Documentation/3.15.0/rest-api-projects.html#get-submit-requirement-templates)
and
[`GET /projects/{project}/submit_requirements_templates/{name}`](https://gerrit-documentation.storage.googleapis.com/Documentation/3.15.0/rest-api-projects.html#get-submit-requirement-template)
REST endpoints.

### Rich Markdown Diff

A rich rendered view for the diff of Markdown files has been introduced, which
can be toggled from the diff view and the file list, with inline word and block
highlighting.

Comments can be added directly in the rendered Markdown view, including with
the `C` shortcut and on a text selection.

### Searching Changes

New search operators have been added to the change index:

* `onlypaths:` finds changes touching exactly the given set of files,
  allowing submit requirements to replace Prolog rules based on the
  exact list of modified files. Magic files such as `/COMMIT_MSG` are ignored, and
  a single regular expression starting with `^` can be used instead of a
  comma-separated list of paths.

  > **NOTE**: Using the operator with a very commonly changed file may produce a
  > large intermediate result set and be expensive.

* `filecount:` finds changes whose latest patch set touches a given number of
  files, e.g. `filecount:>2`.

* `unmet_requirement:'NAME'` and `unsatisfied_requirement_count:'RELATION''NUMBER'`
  find changes by their unmet submit requirements. These operators are not
  allowed inside submit requirement expressions.

* `has:hashtag` matches changes that carry at least one hashtag.

### Committing Files to a Branch via REST API

The new `POST /projects/{project-name}/branches/{branch-id}/commit` REST
endpoint creates, updates, deletes or renames files on a branch in a single
commit, without cloning the repository or creating a change.

The caller needs Push access on the branch; commit and ref-update validators
(including plugin validators) run, but push-only receive-pack checks are not
applied and matching open changes are not auto-closed.

An optional `base_revision` rejects the request with `409 Conflict` if the
branch has moved, and a request that would not change the tree is rejected with
`400 Bad Request`.

### OAuth Tokens Lifecycle

For sites using OAuth authentication (`auth.type = OAUTH`), OAuth token handling
now covers the whole token lifecycle. The `OAuthServiceProvider` extension point
supports OAuth 2.0 with PKCE (Proof Key for Code Exchange) and can refresh and
revoke tokens, with a new `OAuthTokenRevokedListener` extension point notified
on revocation; existing providers remain compatible. Expired access tokens are
renewed from their refresh token when the provider supports it, including when
[retrieved through the REST API](https://gerrit-documentation.storage.googleapis.com/Documentation/3.15.0/rest-api-accounts.html#get-oauth-token), and a
failed refresh is retried after [`auth.oauthTokenRefreshInterval`](https://gerrit-documentation.storage.googleapis.com/Documentation/3.15.0/config-gerrit.html#auth.oauthTokenRefreshInterval).
Tokens stored in the [`oauth_tokens` cache](https://gerrit-documentation.storage.googleapis.com/Documentation/3.15.0/config-gerrit.html#cache.oauth_tokens)
are encrypted at rest with AES-256-GCM using
[`auth.tokenEncryptionKey`](https://gerrit-documentation.storage.googleapis.com/Documentation/3.15.0/config-gerrit.html#auth.tokenEncryptionKey),
which `init` generates automatically. PKCE, token refresh and token revocation
take effect only when the OAuth provider plugin implements the new extension
point methods; the [oauth plugin](https://gerrit.googlesource.com/plugins/oauth)
supports all of them.

### Administration & Configuration

* **Stale change index recovery**

  Gerrit can now automatically recover change index updates that were lost when
  the process crashed or was interrupted between the NoteDb write and the index
  write. Enable it with `index.staleChangeRecovery = true` (default `false`):
  Gerrit writes per-change intent files under `$site_path/data/pending-index/`,
  recovers leftovers from a crashed process at startup and runs a background
  scanner every `index.staleChangeRecoveryInterval` (default `5m`).

  > **NOTE**: Recovery is only effective when `index.commitWithin` is set to zero
  > and `index.indexChangesAsync` is false.

### High-Availability Configuration

  The new `index.directory` setting configures where Gerrit stores its index
  independently of the site path (default `$site_path/index`; relative paths are
  resolved against `$site_path`).

### Auth Token Expiry Notifications

Users are now notified not only before one of their authentication tokens
expires, but also once it has expired. The notification schedule is no longer
fixed at 7 days before expiry: it is configured with
[`auth.token-expiry.notifyDaysBefore`](https://gerrit-documentation.storage.googleapis.com/Documentation/3.15.0/config-gerrit.html#auth.token-expiry.notifyDaysBefore),
which can be set multiple times (default 0, 7, 14 and 21 days), and can be
switched off with
[`auth.token-expiry.notify`](https://gerrit-documentation.storage.googleapis.com/Documentation/3.15.0/config-gerrit.html#auth.token-expiry.notify).
The notifier runs daily at midnight and sends at most one email per token per
day.

### Refreshed Web UI

The header bar now shows the Diffy logo on the top-left, and the sign-in pages
have been restyled. The web UI no longer ships Polymer; plugins that still use
it need to migrate (see Breaking Changes).

## Important Notes

### Schema and index changes

Gerrit schema version is updated to `187` (Gerrit v3.13 and v3.14 are both
on `185`):

* `Schema_186` grants the new `postReviewComment` permission to Registered
  Users on `refs/*` in `All-Projects`.
* `Schema_187` grants the `aiReview` permission to Registered Users on
  `refs/heads/*` in `All-Projects`, unless an `aiReview` rule already exists
  there, so that the switch to the default-deny model keeps the previous
  behavior.

The Changes index has been upgraded to `v90` (Gerrit v3.13 is on `v87`, v3.14
on `v88`) and requires a full reindex: `v89` adds the unmet-requirement and
unsatisfied-requirement-count fields, and `v90` adds the file count field. The
Accounts, Groups and Projects index versions are unchanged.

### Offline upgrade

- Stop Gerrit
- Download the new `gerrit.war` and move it to `$GERRIT_SITE/bin`
- Extract all the plugins from `gerrit.war` and move the ones needed into `$GERRIT_SITE/plugins`
- Run init to apply the schema migrations:
  `java -jar $GERRIT_SITE/bin/gerrit.war init --batch -d $GERRIT_SITE`
- Run the full reindex:
  `java -jar $GERRIT_SITE/bin/gerrit.war reindex --index changes -d $GERRIT_SITE`
- Start Gerrit

> **NOTE**: The released `gerrit.war` needs a Java 25 runtime, see
  [Java 25](#java-25).

### Online upgrade with zero-downtime

Gerrit v3.15.x supports zero-downtime upgrade from Gerrit v3.13 or v3.14 when
configured using a
[high-availability](https://gerrit.googlesource.com/plugins/high-availability/+/refs/heads/master/README.md)
setup.

During the zero-downtime upgrade, Gerrit end-users will not experience any
outage or service disruption and will be able to perform any read/write Gerrit
operation seamlessly.

The zero-downtime upgrade process for high-availability setups
consists of the following steps ([demo](https://youtu.be/vK5qsb0W7q4)):

1. Have Gerrit servers running v3.13/v3.14 in high-availability
   configuration, healthy and able to handle the incoming traffic properly.
2. Set one of the Gerrit servers to unhealthy.
3. Shutdown the Gerrit server, update gerrit.war, plugins and libs to v3.15.x and start Gerrit again.
4. Verify that the Gerrit server is working properly (e.g. run automated smoke
   tests) and then make it healthy again.
5. Ensure the Gerrit server is fully caught up with the events that happened while
   it was down before directing traffic to it.
6. Repeat steps 2 to 6 for each of the remaining Gerrit servers.

> **NOTE**: The schema version changes from `185` to `187`. Set
  [`gerrit.experimentalRollingUpgrade = true`](https://gerrit-documentation.storage.googleapis.com/Documentation/3.15.0/config-gerrit.html#gerrit.experimentalRollingUpgrade)
  on all the Gerrit servers for the duration of the upgrade; without it, the
  v3.13/v3.14 servers refuse to start once the first server has migrated the schema.
  Remove the setting once all the servers run v3.15.

### Downgrade

Downgrade to Gerrit v3.13 or v3.14 is possible, but requires the following manual steps:

1. Stop Gerrit
2. Set `gerrit.experimentalRollingUpgrade = true` in `gerrit.config`: v3.13/v3.14
   refuses to start on schema version `187` otherwise
3. Rollback the gerrit.war and plugins to the previous v3.13/v3.14 version
4. Run the full reindex with the v3.13/v3.14 `gerrit.war`, because the old
   `v87`/`v88` Changes index does not contain the updates made while running
   v3.15:
   `java -jar $GERRIT_SITE/bin/gerrit.war reindex --index changes -d $GERRIT_SITE`
5. Start Gerrit

The `postReviewComment` and `aiReview` grants added by the schema migrations
stay in `All-Projects`:

* Gerrit v3.14 applies the `aiReview` grant, so Registered Users keep AI Review
  on `refs/heads/*` as before. It ignores the `postReviewComment` grant, which
  it does not know.
* Gerrit v3.13 knows neither permission and ignores both grants.

* [Issue 309098227](https://issues.gerritcodereview.com/issues/309098227) [Change 360646](https://gerrit-review.googlesource.com/360646):
The introduction of a per-request ref cache for better performance may break
the repository consistency

  The addition of a new `core.usePerRequestRefCache` setting, true by
  default, introduced a per request (currently per request thread) ref
  cache, helping reduce the overhead of checking if the packed-refs file
  was outdated. However, in some scenarios, such as multi-site or
  concurrency between `git-receive-pack` and `git-gc`, it may lead to
  split-brain inconsistencies and, in the worst-case scenario, to the
  corruption of the underlying repository.

* [Issue 380898784](https://issues.gerritcodereview.com/issues/380898784):
The new `changes_by_project` cache will make the `git-upload-pack` fail intermittently
on projects containing one or more inconsistent changes.

  The introduction of the `changes_by_project` cache is incompatible with projects
  having one or more inconsistent changes, like changes with /meta refs coming from
  unexpected Gerrit serverId.
  The cache makes the `git-upload-pack` fail intermittently
  with internal server errors when it fails to load the change meta-data depending
  on the status of the cache.
  As a workaround, disable the `changes_by_project` cache as follows in `gerrit.config`:
  ```
  [cache "changes_by_project"]
        memoryLimit = 0
  ```

## Breaking Changes

* [Change 586901](https://gerrit-review.googlesource.com/c/gerrit/+/586901):
  Switch the `aiReview` permission to the standard default-deny model

  Previously `aiReview` was allowed for everyone when no rules were configured,
  and `DENY` or `BLOCK` rules alone could restrict groups. On upgrade, a NoteDb
  schema migration (`Schema_187`) adds an explicit grant for Registered Users on
  `refs/heads/*` to `All-Projects`, unless that section already has an
  `aiReview` rule. New sites are seeded with the same grant, so the
  out-of-the-box behavior is preserved. Sites that restricted `aiReview` with
  `DENY` or `BLOCK` rules must review them: if `All-Projects` already had such a
  rule on `refs/heads/*`, no grant is added and nobody has access, and a `DENY`
  no longer excludes a subgroup from the broad grant.

* [Issue 40009784](https://issues.gerritcodereview.com/issues/40009784),
  [Change 624061](https://gerrit-review.googlesource.com/c/gerrit/+/624061):
  Reject implicit merges on submit by default

  `receive.rejectImplicitMerges` (default `true`) now applies to submit as well
  as push, so submitting a change that would implicitly merge another branch is
  rejected unless the project sets it to `false`. The
  `GerritBackendFeature__check_implicit_merges_on_merge`,
  `GerritBackendFeature__reject_implicit_merges_on_merge` and
  `GerritBackendFeature__always_reject_implicit_merges_on_merge` experiments
  were removed.

* [Change 637103](https://gerrit-review.googlesource.com/c/gerrit/+/637103):
  Deprecate the `refs/for` `Push Merge Commit` fallback for direct merge pushes

  Direct merge pushes authorized only through a `Push Merge Commit` grant on
  `refs/for` now log a throttled warning. The fallback still works but will be
  removed in a future release; grant `Push Merge Commit` on the destination ref
  instead.

* [Change 617061](https://gerrit-review.googlesource.com/c/gerrit/+/617061):
  Require all comments in a thread to be on a single patchset

  This was previously enforced only by the frontend. The backend now rejects a
  reply (`in_reply_to`) on a different patchset than its parent comment with
  `400 Bad Request`, both when posting a review and when creating or updating a
  draft comment. Clients that replied to comments on several patchsets in one
  review request must split the request by patchset.

* [Change 622261](https://gerrit-review.googlesource.com/c/gerrit/+/622261):
  Fix `httpd.acceptorThreads` being applied to Jetty selector threads and add
  `httpd.selectorThreads`

  `httpd.acceptorThreads` was previously passed as the selector count. It now
  governs acceptors (default 0), and the new `httpd.selectorThreads` (default 2)
  controls selectors. Sites that raised `httpd.acceptorThreads` for I/O
  concurrency should set `httpd.selectorThreads` instead.

* [Change 614121](https://gerrit-review.googlesource.com/c/gerrit/+/614121):
  Change the format of push warnings

  Warnings printed by `git push` (for example
  `pushing without Change-Id is deprecated` or `no files changed`) now start
  with an upper-case `WARNING:` instead of `warning:`, and the
  `no files changed` warnings add a `commit` prefix before the abbreviated
  commit hash, aligning them with other validators. Tools parsing push output
  may need adjusting.

* [Issue 40014461](https://issues.gerritcodereview.com/issues/40014461),
  [Change 577286](https://gerrit-review.googlesource.com/c/gerrit/+/577286):
  Include the project name in `ChangeIndexedListener#onChangeDeleted`

  The method changes from `onChangeDeleted(int id)` to
  `onChangeDeleted(String projectName, int id)`, and `ChangeIndexer#delete` now
  also takes the project. Change numbers are unique per project rather than per
  installation, so the number alone does not identify the change to delete.
  Plugins implementing `ChangeIndexedListener` must be adapted.

* [Issue 515272357](https://issues.gerritcodereview.com/issues/515272357),
  [Change 581621](https://gerrit-review.googlesource.com/c/gerrit/+/581621):
  Require `project~changeNumber` change IDs for deletions in
  `POST /config/server/index.changes`

  When `delete_missing` is `true`, every entry in `changes` must use the
  `project~changeNumber` format. Otherwise the request fails with
  `400 Bad Request` and no changes are reindexed or deleted, which prevents the
  wrong change from being deleted from the index.

* [Change 626021](https://gerrit-review.googlesource.com/c/gerrit/+/626021):
  Type `RevisionInfo.ParentInfo#changeStatus` as `ChangeStatus` enum instead of
  `String`

  Java extension API consumers must adapt from `String` to `ChangeStatus`. The
  REST JSON wire format is unchanged.

  (e.g. `maven.install`), scoped to the plugin as documented.

  Remove the `provided_deps` attribute from the `gerrit_plugin` Bazel API

  Support for `provided_deps` was already removed in bazlets. Plugin BUILD files
  that still pass `provided_deps` to `gerrit_plugin` must drop it.

* [Issue 303819949](https://issues.gerritcodereview.com/issues/303819949),
  [Change 520342](https://gerrit-review.googlesource.com/c/gerrit/+/520342):
  Migrate the frontend build to `rules_nodejs` 6.x, bzlmod and pnpm

  The frontend build now uses the Aspect rules (`rules_js`, `rules_ts`,
  `rules_rollup`, `rules_terser`) with pnpm, while `yarn.lock` stays the
  authoritative lockfile. `tools/bzl/js.bzl` is kept as a compatibility layer;
  plugins should switch their loads to
  `@com_googlesource_gerrit_bazlets//js:defs.bzl` for `gerrit_js_bundle` and
  `js_component`.

* [Change 631801](https://gerrit-review.googlesource.com/c/gerrit/+/631801):
  Deprecate `DynamicSet.contains()` for removal

  The method scans all registered items and is inherently slow. Plugins should
  stop using it; it will be removed in a future release.

* [Change 553022](https://gerrit-review.googlesource.com/c/gerrit/+/553022),
  [Change 553181](https://gerrit-review.googlesource.com/c/gerrit/+/553181),
  [Change 582202](https://gerrit-review.googlesource.com/c/gerrit/+/582202),
  [Change 585681](https://gerrit-review.googlesource.com/c/gerrit/+/585681):
  Remove Polymer from the frontend

  The UI no longer loads Polymer: the global `Polymer` object is gone, Polymer
  style includes such as `gr-change-view-integration-shared-styles` no longer
  work, and `@polymer/polymer` and `@polymer/decorators` were removed from
  `plugins/package.json`. Plugins that still use Polymer fail to load and must
  be migrated to Lit. `LitElement`, `html` and `css` are exposed on `window`,
  and the change view integration styles are available as
  `Gerrit.styles.changeViewIntegration`.

## Performance Changes

* [Change 637343](https://gerrit-review.googlesource.com/c/gerrit/+/637343),
  [Change 636443](https://gerrit-review.googlesource.com/c/gerrit/+/636443):
  Share the All-Users repository handle across account lookups

  Improves account cache performance by avoiding reopening `All-Users` and
  recomputing its file key on each account lookup.

* [Change 638024](https://gerrit-review.googlesource.com/c/gerrit/+/638024):
  Enable compact object headers by default on JDK 25 via site init

  On JDK 25, `gerrit init` writes `-XX:+UseCompactObjectHeaders` to
  `container.javaOptions` unless an administrator already enabled or disabled
  it, reducing heap usage. To opt out permanently, set
  `-XX:-UseCompactObjectHeaders`; just removing the option is undone by the next
  `gerrit init`.

* [Change 585386](https://gerrit-review.googlesource.com/c/gerrit/+/585386):
  Open persistent disk caches on a dedicated pool during startup

  The new `cache.startupThreads` option (default `1`), when set above 1, opens
  persistent caches on a dedicated `DiskCache-Store-Startup` pool, separate from
  the `DiskCache-Store` pool that handles cache updates.

* [Change 591501](https://gerrit-review.googlesource.com/c/gerrit/+/591501):
  Warm up H2 cache files for faster bloom filter building

  Reads the whole H2 cache file before building bloom filters so the OS page
  cache is populated. On a production instance with ~84M disk cache entries this
  reduced startup load time from ~22 to ~16 minutes. Controlled by the new
  `cache.preWarmForBloomFilter` option, enabled by default.

* [Change 607261](https://gerrit-review.googlesource.com/c/gerrit/+/607261):
  Skip disk stats by default in `show-caches` and the list-caches REST API

  Collecting disk stats for persistent caches is expensive on busy servers. Use
  the new `--include-diskstats` option to opt in.

  load full line-by-line diffs for every listed file. The returned `FileInfo`
  entries then omit line counts and sizes.

## Permissions & Security Changes

* [Change 454501](https://gerrit-review.googlesource.com/c/gerrit/+/454501):
  Add the `postReviewComment` permission and a schema migration to grant it by
  default

  The new `postReviewComment` permission prepares for posting review comments
  without label voting permission; it is not enforced yet in 3.15. A NoteDb
  schema migration (`Schema_186`) grants it on `refs/*` to Registered Users in
  `All-Projects`, unless the permission is already configured there, and new
  sites are seeded with the same grant. For online upgrades, all hosts must run
  the migration before the permission is enforced, so users without label voting
  permission can keep posting comments.

* [Issue 40001199](https://issues.gerritcodereview.com/issues/40001199),
  [Change 636985](https://gerrit-review.googlesource.com/c/gerrit/+/636985):
  Allow direct merge pushes authorized by `Push Merge Commit` on the destination
  ref

  Previously `Push Merge Commit` was always checked on the `refs/for/` ref, even
  for direct pushes. Direct merge pushes are now authorized by the grant on the
  destination ref, and a grant on `refs/for/` still works as a deprecated
  fallback. `skip-validation` now requires `Push Merge Commit` on the
  destination ref and no longer falls back to `refs/for`, so sites that granted
  it only on `refs/for/` must add the grant on the destination ref. For plugins,
  `RefPermission.MERGE` is now checked on the ref itself rather than on
  `refs/for/<ref>`.

* [Issue 561066231](https://issues.gerritcodereview.com/issues/561066231),
  [Change 630421](https://gerrit-review.googlesource.com/c/gerrit/+/630421):
  Encrypt stored OAuth tokens via `auth.tokenEncryptionKey`

  Tokens in the `oauth_tokens` cache are encrypted with AES-256-GCM when
  `auth.tokenEncryptionKey` holds a base64 128/192/256-bit key. For
  `auth.type = OAUTH` sites, init generates the key into `secure.config` on new
  installs and upgrades; an existing key is never overwritten. Sites that do not
  run init must set the key themselves (for example with
  `openssl rand -base64 32`); while it is unset, tokens are stored in cleartext
  and a warning is logged at startup. Pre-existing cleartext entries stay
  readable. Plugins may still override the `OAuthTokenEncrypter` extension
  point.

* [Issue 565075161](https://issues.gerritcodereview.com/issues/565075161),
  [Change 634365](https://gerrit-review.googlesource.com/c/gerrit/+/634365),
  [Change 634366](https://gerrit-review.googlesource.com/c/gerrit/+/634366): Use
  a strong `SecureRandom` instead of `SHA1PRNG` and `Math.random()` for
  generated secrets

  OAuth state values, the signed-push seed, auth tokens, Change-Ids and
  group/approval UUID salts now use the platform's default cryptographically
  strong RNG. OAuth state values switch to unpadded base64url with the same
  256-bit entropy. No persisted formats change.

* [Change 599041](https://gerrit-review.googlesource.com/c/gerrit/+/599041),
  [Change 609682](https://gerrit-review.googlesource.com/c/gerrit/+/609682):
  Enforce account visibility in the Query Accounts REST endpoint

  `GET /accounts/` returned details of accounts not visible to the caller when
  the `o=DETAILS` option or a suggest query was used. Results are now filtered
  by account visibility, and unless `accounts.visibility` is `ALL`, anonymous
  callers no longer get detailed account fields such as names and emails.

* [Change 633202](https://gerrit-review.googlesource.com/c/gerrit/+/633202):
  Include the sender email address alongside the display name in change emails

  Change email text now shows the acting user as `Name <email>` (the `fromName`
  template parameter) instead of only the display name. This prevents users with
  generic or deceptive display names from making change emails appear to
  attribute actions to the recipient or another user. Customized email templates
  that compare `fromName` may need updating.

### Replication plugin

* [Change 577141](https://gerrit-review.googlesource.com/c/plugins/replication/+/577141):
  Add a `--ref <RefName>` option to the `replication start` command to replicate
  a single branch or tag, not the whole project.

* [Change 585701](https://gerrit-review.googlesource.com/c/plugins/replication/+/585701):
  Auto-repair replication when a push fails with a "missing necessary objects"
  error on plain SSH destinations. This is controlled by the new
  `autoRepairMaxAttempts` (default `0`, disabled), `autoRepairInterval` and
  `autoRepairConcurrencyLimit` settings.

  Related improvements to the project repairer:
  * [Change 616286](https://gerrit-review.googlesource.com/c/plugins/replication/+/616286):
    New `--copy-loose-objects` repair action, also covered by `--full`.
  * [Change 620401](https://gerrit-review.googlesource.com/c/plugins/replication/+/620401)
    [Change 620402](https://gerrit-review.googlesource.com/c/plugins/replication/+/620402):
    Rsync from a hardlink snapshot so repacks during the copy do not break it,
    and delete stale snapshots before each repair.
  * [Change 616281](https://gerrit-review.googlesource.com/c/plugins/replication/+/616281):
    Run rsync with `--progress` rather than `-P`, so an aborted transfer does
    not leave truncated files behind.

* [Change 588841](https://gerrit-review.googlesource.com/c/plugins/replication/+/588841):
  New `replication.emitEvents` option (default `true`) to turn off replication
  stream events when nothing consumes them.

* [Change 610643](https://gerrit-review.googlesource.com/c/plugins/replication/+/610643):
  Allow `remote.NAME.threads = 0` to put a remote in persist-only mode. In this
  mode the node only writes replication tasks to the task storage and another
  primary does the pushes. This is useful in multi-primary deployments.

* [Change 622501](https://gerrit-review.googlesource.com/c/plugins/replication/+/622501):
  `remote.NAME.replicationRetry` now accepts an optional time-unit suffix (e.g.
  `30 s`). A bare number still means minutes.

* [Change 612842](https://gerrit-review.googlesource.com/c/plugins/replication/+/612842):
  Apply `excludedRefsPattern` before scheduling tasks, so excluded refs are no
  longer queued and persisted as no-op work.

* [Change 616001](https://gerrit-review.googlesource.com/c/plugins/replication/+/616001):
  Stop the distributor from re-firing tasks that are already pending. This
  removes a steady growth of the pending task's state on each cycle.

* [Change 611961](https://gerrit-review.googlesource.com/c/plugins/replication/+/611961):
  Show batch progress for running batched pushes in the task queue.

* [Change 609701](https://gerrit-review.googlesource.com/c/plugins/replication/+/609701):
  Include exception data, such as stack traces, in the replication log when JSON
  logging is used.

* [Change 635127](https://gerrit-review.googlesource.com/c/plugins/replication/+/635127):
  When `replication start` schedules nothing, say why in a clearer warning: no
  destination matched, or the authGroup cannot read the projects.

* [Change 611861](https://gerrit-review.googlesource.com/c/plugins/replication/+/611861):
  Document that `excludedRefsPattern` takes a Java regular expression that must
  match the whole ref name.
